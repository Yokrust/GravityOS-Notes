# Project-first thread model and retrospective Folder View

> Status: Superseded by `0014-folder-view-removal.md`.

Gravity will use **Project** as the canonical user-facing term for the folder-backed working environment the user selects for agent work. This replaces **Folder System** in product language. Gravity will model agent continuity through **Thread** as the shared parent concept, with two concrete thread types: **Conversation Thread** for discussion without project access, and **Project Thread** for project-attached interaction that can execute **Runs** against exactly one **Project**. Sidebar navigation is split into an always-visible **Chats Header** for **Conversation Threads** and an always-visible **Projects Header** containing expandable per-project **Project Groups**. Those top-level section labels remain visible even when their sections are empty. Attaching a project from a conversation upgrades that same thread in place into a **Project Thread** instead of creating a duplicate thread, and its sidebar rendering moves from the **Chats Header** into the owning **Project Group**. That transition is one-way, and a **Project Thread** remains permanently bound to its selected **Project** for its entire lifetime. The prompt-adjacent project-transfer affordance exists only before that upgrade and disappears afterward because a **Project Thread** cannot be moved to another **Project** or used to create a different project-bound thread. Any in-progress draft prompt remains in the composer across the upgrade so the user can continue editing it or submit it after project attachment. The first later **Run** in that upgraded **Project Thread** inherits the earlier thread conversation history through thread continuity, even though pre-upgrade discussion does not become retroactive project replay content. Canceling project selection or creation leaves the thread as a **Conversation Thread** with no project binding and no draft loss. Project selection is revalidated when the upgrade is committed, and if the selected project is no longer available the thread remains unchanged. If new assistant activity arrives while the transfer flow is open, Gravity closes that flow and clears its temporary selection state before any upgrade can occur. While the agent is still responding, the project-transfer affordance is visible only as a disabled ghost-state control and cannot upgrade the thread; clicking it does nothing, with any optional passive hover tooltip explaining only the temporary blocked state. Expanding or collapsing a **Project Group** affects only sidebar visibility and never changes which **Thread** remains rendered in the **Thread Panel**, and thread upgrade never auto-expands the destination **Project Group**. The currently rendered thread carries the active sidebar highlight, and when an active conversation thread upgrades that highlight moves atomically into the destination project-thread row. A **Project Group** never enters an active selected state and may only show hover styling as a container.

Gravity will also reposition **Folder View** as a retrospective audit surface instead of the primary live execution surface. During an active **Run**, Folder View may show lightweight provisional awareness signals derived primarily from the **Agent Activity Stream** and secondarily refined by filesystem observation, but it does not promise a complete live reconstruction. After a run completes, the completed **Trace** becomes immediately replayable, and **Folder View** becomes the primary spatial surface for retrospective **Trace** review. For one selected **Project Thread**, Gravity provides **Thread Replay**, the thread-scoped retrospective replay experience that navigates across completed runs while replaying one selected run's project-shaped behavior at a time from its per-run **Trace**. When a **Conversation Thread** is upgraded in place, its prior messages remain part of the same thread continuity in the **Thread Panel**, but they do not retroactively become project-shaped replay content. Folder View remains primarily trace-driven: it does not display the full **Agent Activity Stream** directly, and may use only trace-compatible activity overlays when useful. The **Trace Details Panel** remains a separate structured retrospective inspection surface for one selected **Project Thread**.

This decision supersedes the parts of earlier ADRs that no longer match the product direction:

- `0001-folder-system-first-architecture.md` is superseded where it defines **Folder System** as the primary product object and frames Gravity mainly around folder-system-first interaction language.
- `0002-persisted-trace-model.md` is superseded where it frames live trace updates around the older Folder View model.
- `0005-run-thread-scoped-trace-inspection.md` is superseded where it uses **Run Thread** as the canonical thread term and ties retrospective inspection language to that older model.
- `0007-agent-attributed-trace-events.md` is superseded where it speaks in folder-system-first language and frames trace around the older execution model.
- `0006-canvas-folder-view.md` is superseded where it treats **Folder View** as the primary differentiated execution-time surface rather than a replay-first retrospective surface.

The trade-off is that Gravity moves closer to a familiar agent-chat interaction model for active work while preserving differentiation in project observability and retrospective review. Gravity accepts a clearer split of responsibilities across surfaces in exchange for dropping the brittle promise of exhaustive live spatial observability.
